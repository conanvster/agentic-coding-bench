# Правила моделей — як стенд обходить знайдені проблеми (з 29.10.2026)

Кожна знайдена проблема моделі чи рушія має стати **налаштуванням у файлі правил**, а не правкою коду чи
пам'яттю «у gpt-oss треба…». Правила читають `proxy.py` (на старті) і `run-v3.sh` (перед завантаженням моделі).

## Де лежать

```
model-rules/
  _загальні.json             — типові значення для всіх + проблеми стенду, не прив'язані до моделі
  gpt-oss-20b.json           — один файл на модель; ключ LM Studio — у полі "model", ТОЧНИЙ збіг
  qwen3.6-35b-a3b.json …
model_rules.py               — завантаження і зведення; CLI для перевірки
lib-graphs.sh                — перемикання CUDA-графів (перезапуск демона LM Studio)
lib-direct.sh                — модель на llama-server напряму (поле server)
qa/check-pre.sh, accept-pre.py — незалежна перевірка коду претесту (docker + 11 перевірок за ТЗ)
```

Без «родин» і префіксів: усе, що діє на модель, видно в її файлі, крім `_загальні.json`.
Нова модель без файлу отримує лише загальні правила, і `run-v3.sh` пише «УВАГА: немає файлу правил».

Перевірити, що отримає модель: `python3 model_rules.py openai/gpt-oss-20b` (усе) або `… graphs` (одне поле).
Список файлів і дублікати ключів: `python3 model_rules.py --check`.

## Поля

| Поле | Хто читає | Що робить |
|---|---|---|
| `model` | обидва | ключ LM Studio (як у `lms ps`) |
| `опис` | людина | квант, розмір, зір, роль |
| `sampling` | proxy.py | дописується в кожен запит (OpenCode сам не шле temperature/top_p) |
| `reasoning_effort` | proxy.py | рівень міркування (gpt-oss: high; типовий у LM Studio — low) |
| `passback` | proxy.py | `{field, keep}` — у яке поле повертати моделі її попередні міркування і за скільки останніх кроків |
| `peg_retries` | proxy.py | скільки разів тихо повторити запит при «peg-native»; з 30.10 — 0 (повтор без seed давав ту саму зламану відповідь) |
| `seed` | proxy.py | `"random"` — випадковий seed у кожен запит (LM Studio без нього відповідає детерміновано) |
| `server` | run-v3.sh, proxy.py | `{"kind": "llama-server", "port": N, "gguf": "…", "args": [...]}` (args — додаткові параметри llama-server, напр. кеш K/V q8_0) — модель іде на llama-server напряму, без LM Studio (lib-direct.sh); проксі шле її запити на цей порт, рівень міркувань — ще й у chat_template_kwargs |
| `graphs` | run-v3.sh | `on`/`off` — CUDA-графи llama.cpp; 4-те поле runs-файлу `graphs=on|off` перекриває |
| `issues` | людина | знайдені проблеми (формат нижче) |
| `результати` | людина | підсумок моделі в кожному прогоні (етапи, час, токени, якість коду) |

Контекст і slug — у `runs-v3.txt` (вони про прогін, а не про модель).

## Як записувати проблему (`issues`)

```json
{"id": "gemma-edit-args",
 "symptom": "що видно: точний текст помилки, де саме",
 "cause": "чому — якщо встановлено; «підозра» — якщо ні",
 "workaround": "яким ПОЛЕМ цього файлу обходиться (або «шукається: чим перевіряємо»)",
 "status": "ВІДКРИТО | обхід перевірено (як, цифри) | закрито",
 "seen": "де і коли спостерігали",
 "link": "issue в llama.cpp / LM Studio / OpenCode"}
```

Порядок роботи з новою проблемою:
1. Записати `issues` зі `status: ВІДКРИТО` у файл моделі (або в `_загальні.json`, якщо не від моделі).
2. Відтворити окремо від прогону (скрипти `*_replay.py`, `stress_xid.py`, `speed_bench.py`), з цифрами.
3. Обхід — значенням поля правил; якщо поля для цього ще нема — додати поле в `proxy.py`/`run-v3.sh` і в таблицю вище.
4. Перевірити обхід тим самим відтворенням → `status` з цифрами.
5. Правила змінюються **лише між прогонами** (proxy.py читає їх раз на старті) — рівні умови всередині прогону.
